## 3. Существующие финансовые компоненты и состояние платежей

### Действующий поток

```text
Запись / корзина / ручная платёжная ссылка
  → серверная проверка состава, суммы, скидки и доступа
  → pending orders + резервы PostgreSQL
  → Т-Банк Init → PaymentURL → платёжная форма банка
  → подписанный /api/payment/callback
  → transitionOrderState → приём / остатки / лояльность / уведомления

Cron cancel-pending → GetState / Cancel → согласование части зависших заказов
Неопределённый Init → payment_cases → ручная проверка
```

Проверены исходники `/api/payment/init`, `/callback`, `/status`, `/cancel`, `/api/admin/payment-links`, `/api/admin/orders`, `/api/cron/cancel-pending`. Провайдер — Т-Банк. Секреты и значения production env в документ не включаются.

- Init сверяет цену с БД, доступ к приёму и snapshot, не доверяет сумме клиента. Повторная оплата приёма ограничена резервированием и поиском существующего заказа.
- Callback проверяет подпись и сумму CONFIRMED, допускает восстановление связи по OrderId, не возвращает отменённую запись к жизни при поздней оплате. Token удаляется перед сохранением payment_data.
- `transitionOrderState` блокирует строку и проверяет допустимый исходный статус. Это полезная существующая защита от повторов, но не долговечный журнал всех событий провайдера.
- После изменения заказа приём/лояльность/уведомления обновляются отдельными шагами. Для нового реестра нужен транзакционный outbox и повторяемая обработка, а не предположение об атомарности всего callback.
- GetState/Cancel используют другой транспорт из tbank.ts с иными тайм-аутами. Унификация возможна отдельным изменением с тестами, не сделана на этапе 0.
- `/api/qr` рисует QR произвольной строки/ссылки. Это НЕ банковская интеграция СБП. Вызовы GetQr/GetQrState в просмотренном коде не обнаружены. СБП на hosted-форме может зависеть от терминала; включение у провайдера не проверено. [Официальный раздел СБП Т-Банка](https://developer.tbank.ru/eacq/api/sbp).

### Фискализация

Init передаёт Receipt; в коде зафиксированы `PaymentMethod: full_payment`, `Tax: none`, fallback `Taxation: usn_income`. Это входные параметры, не подтверждение зарегистрированной ККТ и не подтверждение успешного чека. Нет отдельной FiscalReceipt, фискальных реквизитов/статусов, самостоятельного обработчика фискальных уведомлений и прослеживаемого закрывающего чека.

Применимость full_payment к оплате будущего приёма требует проверки: ФНС отдельно описывает чек предоплаты и зачёт при оказании услуги. Нельзя автоматически использовать один признак для всех сценариев. [ФНС: ККТ, предоплата и окончательный расчёт](https://kkt-online.nalog.ru/faq/). Т-Банк различает уведомления платежей и фискализации: [официальные уведомления](https://developer.tbank.ru/eacq/intro/developer/notification).

### Возвраты и сверка

Cancel доступен администратору либо cron-secret. `/api/payment/cancel` вызывает провайдера по PaymentId до поиска pending-заказа. Отдельной заявки возврата, лимита суммы возвратов, персонального согласования и причины нет. Доработка должна отличать отмену неоплаченного платежа от возврата уже полученных денег.

Полный REFUNDED меняет статус заказа; PARTIAL_REFUNDED только перезаписывает payment_data. Нет истории отдельных возвратов, суммы возврата по строкам, состояния возвратного чека и независимого налогового сторно. Payment cases позволяют отметить внешнее урегулирование, но это не подтверждение банковского возврата.

Время paid_at устанавливается обработчиком как текущее время, не хранит отдельно время события банка. Дат фискализации, зачисления и признания налогового дохода нет. Выписка банка, комиссии и распределение пакетного зачисления между платежами не интегрированы.

### Снимок действующей БД

Проверка выполнена транзакцией `BEGIN READ ONLY` с statement_timeout=5s и ROLLBACK. Схема: 34 таблицы public; миграции 001–020 присутствуют в schema_migrations. orders.total/amount_paid/subtotal/discount_amount и service_prices.price — NUMERIC(12,2). Названия/типы проверены в information_schema, не только по файлам миграций.

На момент аудита за последние двое суток: три заказа со статусом cancelled; три открытых случая payment_init_uncertain. Эта выборка не является отчётом о выручке за весь срок. Изменений статусов не выполнялось. Успешную оплату после предыдущего исправления этой выборкой подтвердить нельзя. Старые результаты диагностики не заменяют актуальную банковскую сверку; в данном этапе банковские методы не вызывались.

## 5. Предлагаемая архитектура

Модульный монолит: `src/lib/finance/*` + `/api/admin/finance/*` + существующая PostgreSQL. Существующий Т-Банк оборачивается адаптером, не создаётся второй независимый эквайринг. Redis используется для кэша/сессий, но не для единственной защиты денег от дублей.

### Сущности (предложение, миграций сейчас нет)

| Сущность | Назначение и ключевые ограничения |
|---|---|
| FinanceTransaction | Факт движения/ожидания денег, RUB, amount_minor, направление, источник, order_id, service/account links, occurred_at/recorded_at, состояние, provenance |
| PaymentEvent | Неизменяемое событие банка: provider/account/payment/order IDs, тип/состояние/сумма, occurred_at/received_at, checksum, проверка подписи, dedup key; статус обработки отдельно от факта |
| FiscalReceipt | Чек, тип расчёта, строки/НДС/способ оплаты, связь с платежами, provider request ID, фискальные ФН/ФД/ФП, status, fiscalized_at; URL хранится с контролем доступа |
| Refund | Заявка/исполнение возврата: исходный платёж, сумма, reason, actor/approver, idempotency key, provider ID/status, refunded_at; отдельный возвратный чек |
| BankSettlement | Строка/пакет выписки, дата зачисления, gross/fee/net, валюта, external ID; дочерние allocations для нескольких платежей и корректировок |
| TaxLedgerEntry | Налоговый факт/корректировка, source event, tax date, сумма, версия правил и профиля, документ-основание; связь с отменяемой записью, без перезаписи истории |
| AuditEvent | actor ID/type, permission/action, entity, request/correlation ID, причина, редактированный diff, timestamp; секреты и платёжные токены исключены |

Дополнительные служебные структуры: durable outbox/jobs, idempotency requests, tax profile/rule versions, receipt allocations, settlement allocations, staff permissions. Их необходимость связана с обеспечением основных сущностей, а не дублированием каталога или клиентов.

Для целых денежных сумм — BIGINT minor units с неотрицательной суммой и отдельным направлением; TS bigint/точный parser, JSON decimal string. Для ставок/дробных количеств — NUMERIC с явными масштабом и правилом округления. Учитывая глобальный int8/NUMERIC parser, финансовые запросы должны получать деньги как text либо иметь локальный type parser; глобальную смену db.ts без регрессий не выполнять. Миграция старых NUMERIC в копейки вычисляется точно в PostgreSQL, не через parseFloat. Нельзя умножать произвольный JS Number и считать это достаточной финансовой моделью.

Точные гарантии: сумма строк чека = сумма чека; сумма распределений = распределяемая сумма; возвраты confirmed+reserved не превышают доступный остаток под блокировкой исходного платежа; уникальность provider identity и idempotency key в БД; корректировки отдельными записями. Возможные округления и скидки распределяются детерминированно в копейках.

Состояния независимы: платёж pending/confirmed/failed/unknown; чек pending/submitted/fiscalized/failed/unknown; возврат requested/approved/submitted/confirmed/failed/unknown; налоговая запись draft/posted/reversed. Банковское CONFIRMED не переводит чек в fiscalized и не задаёт автоматически налоговую дату.

Права: owner, finance_operator, accountant, read_only — конкретные permissions на просмотр, экспорт, принятие денег, возврат, согласование, изменение налогового профиля. Общий legacy-login не должен автоматически получать право реального возврата/кассовой команды. Способ перехода к персональным сотрудникам утверждается отдельно, существующий вход не отключается.

## 6. Схема интеграции и надёжность

```text
Webhook → валидация подписи/терминала/суммы/связи с заказом
        → короткая транзакция: PaymentEvent + dedup + финансовый факт + outbox
        → ACK только после надёжного сохранения
Outbox worker → проекции legacy order/booking + оповещения (идемпотентно)
              → FiscalProviderAdapter → подтверждённый FiscalReceipt
Выписка/реестр банка → BankSettlement → allocations → отчёт расхождений
Подтверждённые источники + TaxProfile/RuleVersion → TaxLedgerEntry → КУДиР
```

На этапе 1 схема не подключена к текущему checkout. На этапе 2 вводить bridge в существующий callback по флагу: текущие контракты ответов не менять. Одна транзакция должна фиксировать финансовое событие и намерение обновить проекции; если нужен общий PoolClient для legacy transition, рефакторинг выполняется только на этапе 2 с тестами. Не отправлять внешние сетевые запросы под блокировкой БД.

Если провайдер даёт уникальный event ID — ключ provider+account+event ID. Иначе утверждается канонический ключ типа события, payment ID, состояния, суммы/возврата и доступного идентификатора операции; одного PaymentId недостаточно. Повторная доставка и retry обработки — разные понятия. Неизвестные подписанные события сохраняются в карантин для сверки, не исчезают из-за отсутствия заказа. Сбой между обработкой и ACK безопасно повторяется.

Неизвестный результат Init/Refund/Receipt: сначала запрос состояния по стабильному request/provider ID; не повторять денежную/кассовую команду вслепую. Retry только с документированной идемпотентностью либо доказанным отсутствием операции. Jobs: ограниченные попытки, backoff, lease, dead-letter/manual review, наблюдаемая задержка. PostgreSQL — источник состояния; worker совместим с текущим Docker/VPS, его production-настройка отдельным разрешённым релизом.

FiscalProviderAdapter: `createReceipt`, `getReceiptStatus`, `getReceiptDetails`, `createRefundReceipt`, `getDeviceStatus`. Нужны capability flags: поддерживаемые ФФД, чеки аванса/зачёта/возврата, наличные, доступность оборудования. Передавать idempotency/request ID. Интернет-касса не считается автоматически пригодной для очных наличных; подтверждение модели и регистрации — gate этапа 4. Test adapter не выдаёт тестовый чек за настоящий и не используется в production-командах.

Планируемые API (НЕ созданы): GET dashboard/transactions/payments/receipts и карточки; POST refunds, cash-payments, reconciliation-runs; GET taxes/kudir; PATCH versioned tax-settings. Все под `/api/admin/finance`, серверные права, cursor pagination, ограниченные фильтры, no-store, аудит экспорта. Экспорты в закрытом хранилище с ограниченным сроком доступа; не публичные uploads. Долгие процессы возвращают operation ID, не утверждают успех до подтверждения провайдера.

KPI определять явно: «получено от клиентов», «возвращено», «зачислено банком», «комиссия», «налоговый доход» — разные величины. Периоды UI по Москве, timestamps БД UTC, налоговая дата отдельным полем. Графики строятся только по подтверждённым фактам, без mock-выручки; если нет данных сверки, показывать «не сверено», а не нулевую комиссию.

## 7. План миграций и отката

Текущий runner: SQL-файлы по порядку, advisory lock, транзакция на файл, таблица schema_migrations. Docker CMD запускает миграции перед приложением. Поэтому простой рестарт новой сборки может применить миграции — production-запуск будущего этапа требует отдельного разрешения.

1. Этап 1: следующие свободные номера после 020 (перепроверить при реализации). Только новые finance/event/audit/outbox/identity tables, FK/unique/check/index. Никаких DROP, переименований существующих таблиц или изменения money parser всего приложения.
2. Этап 2: добавочные allocations/индексы мостов при необходимости; сначала совместимый код с выключенным флагом, затем controlled shadow/reconciliation. Индексы крупных таблиц оценить через EXPLAIN на стенде; CONCURRENTLY не помещать в транзакционный runner без отдельно согласованного механизма.
3. Исторический импорт: отдельная dry-run команда, immutable batch ID и дедупликация, отчёт count/sums, порции. Не приписывать историческим заказам фиктивный чек, зачисление или налоговую дату. Недоказанное — historical_unverified. Импорт не вызывает банк/ККТ и не отправляет письма.
4. После импорта сверить платежи с источниками, чеки — с кассой/ОФД, зачисления — с выпиской. Не включать суммы в окончательную КУДиР до утверждения происхождения.
5. Откат: отключить новые команды/flags, остановить соответствующие jobs штатно, вернуть совместимый образ. Уже полученные события сохранять и оставить безопасный путь приёма callback; выключение UI не должно терять банковские подтверждения. Новые таблицы не удалять. Для внешней финансовой операции нет «отката git»: только подтверждённая компенсирующая процедура.
6. Бэкап: согласованный консистентный backup PostgreSQL, защищённые конфигурации/ключи, артефакт образа и исходники, отдельное хранение и пробное восстановление на стенде. RPO/RTO и срок хранения утвердить; наличие старых source.tar.gz не доказывает восстановимость БД.

Feature flags (пока только проект): `FINANCE_MODULE_ENABLED`, `FINANCE_CASH_ENABLED`, `FINANCE_TAX_ENABLED`, по умолчанию false; проверяются на сервере. Cash и tax дополнительно требуют валидных настроек и отдельного go-live. Флаг не заменяет права доступа. На этапе 0 env не менялся.

## 8. Налоговые и эксплуатационные риски / решения заказчика

Не считать fallback `usn_income` доказательством фактического объекта УСН. До налоговой реализации нужны: объект, ставка и основание региональной льготы, применимый год, наличие сотрудников, история регистрации/смены режима, доходы вне сайта и прошлых периодов, взносы/авансы, НДС/освобождения, даты банковских поступлений. Неизвестная ставка блокирует окончательный расчёт.

Правила версионировать по периодам действия, юрисдикции, объекту, ставке, сотрудникам и НДС. Хранить источник нормы, дату проверки и кто утвердил. Для 2026 года отдельно проверять изменения НДС, не переносить пороги/ставки из 2024–2025. [ФНС: актуальный раздел НДС при УСН](https://www.nalog.gov.ru/rn77/taxation/taxes/nds_usn/).

Форма КУДиР: официальный раздел ФНС указывает приказ от 07.11.2023 № ЕА-7-3/816; перед реализацией экспорта проверить действующую редакцию для выбранного года. [ФНС: УСН и КУДиР](https://www.nalog.gov.ru/rn77/ip/ip_pay_taxes/usn/). PDF/XLSX — будущий результат, на этапе 0 не создавались.

Контрольные сценарии этапа 5 (пока спецификация, расчёты не реализованы):

- Клиент оплатил 10 000 ₽, комиссия 200 ₽, зачислено 9 800 ₽: различить gross/fee/net; при объекте «Доходы» не уменьшать доход на комиссию. [Разъяснение ФНС](https://www.nalog.gov.ru/rn40/taxation/taxes/6221506/). Дату признания проверить по актуальному правилу именно данного платёжного канала и документу.
- Аванс 3 000 ₽ и его последующий зачёт: отсутствие второго денежного дохода только из-за закрывающего чека; возможная доплата отдельным фактом.
- Частичный возврат 1 000 ₽: отдельная операция/возвратный чек/налоговая корректировка с проверенным периодом, без перезаписи исходной оплаты.
- Сотрудников нет / есть: разные допустимые уменьшения, отдельно зафиксированные взносы; ожидаемые числа утверждаются после выбора профиля.
- Граница квартала/года, поздний webhook, рублёвое округление, смена ставки/НДС, поступления вне сайта, повторный импорт выписки.
- Если выбран объект «Доходы минус расходы», нужен реестр допустимых документально подтверждённых расходов и отдельные правила; минимальный модуль «Доходы» его не подменяет.

Проверка ссылок выполнена 08.10.2026. Некоторые отдельные страницы API банка не открылись инструментом; точные контракты фискальных API подлежат повторной проверке перед кодированием.
