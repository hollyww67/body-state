# Настройка уведомлений: Release A / Release B

Ответственный за документ и SMTP-контракт — Макар; интеграция и допуск выпуска — Петрович; инфраструктура — Сеня; проверки — Гриша и QA. Сверено с локальной реализацией и официальными источниками 15.10.2026.

Это инструкция для последующих согласованных действий владельца. Она не подтверждает настройку DNS, работоспособность credentials, модерацию MAX, доставку сообщений или готовность production. В рамках подготовки документа провайдеры, DNS, production и подписки не изменялись; реальные сообщения не отправлялись.

## ENV-контракт

Все значения передаются серверу и worker через защищённое runtime-окружение. Секреты не помещать в Git, отчёты, команды с видимыми аргументами, frontend или переменные `NEXT_PUBLIC_*`. Значения в таблицах — требования и несекретные примеры, а не действующая конфигурация.

| Переменная | Контракт Release A |
| --- | --- |
| `NOTIFICATIONS_EMAIL_V1_ENABLED` | По умолчанию OFF. Только точное `true` включает новый канал; до допуска явно `false`. |
| `SMTP_HOST` | Для Postbox: `postbox.cloud.yandex.net`. Обязательна. |
| `SMTP_PORT` | `587`; отсутствие означает `587`. Новый adapter отклоняет другие порты. |
| `SMTP_SECURE` | `false` или отсутствует: соединение обязательно повышается до TLS через STARTTLS. |
| `SMTP_USER` | ID API-ключа сервисного аккаунта, передать через runtime env. |
| `SMTP_PASSWORD` | Секретная часть этого API-ключа. Не пароль почтового ящика. |
| `SMTP_FROM` | Обязательный проверенный sender, предлагаемый адрес: `Body State <no-reply@body-state.ru>`. Перед использованием подтвердить право отправки. |
| `SMTP_REPLY_TO` | Необязательный один действующий адрес поддержки; отсутствие допустимо, пустую строку не задавать. Владельцу проверить приём ответов. |
| `NOTIFICATION_RESET_KEY` | Обязателен для V1 password recovery: отдельный криптографически случайный секрет, минимум 32 UTF-8 байта. Стабилен между экземплярами приложения и worker. |

Транспорт: `requireTLS=true`, проверка сертификата включена, TLS минимум 1.2, SMTP debug/logger выключены. Никаких `rejectUnauthorized=false` и отключения проверки TLS через env. Новый API: `deliverTransactionalEmail(to, subject, html, text)` возвращает `ProviderResult`; SMTP acceptance не означает доставку в почтовый ящик. При сетевой неопределённости возможен `uncertain`.

Legacy `deliverEmail`/`sendEmail` сохраняют прежние `EMAIL_API_KEY`, `EMAIL_FROM`, `EMAIL_FROM_NAME`, `EMAIL_REPLY_TO`; новый entrypoint не переключается на Resend и требует `SMTP_FROM`. SMTP host/port/user/password общие с legacy: их замена способна изменить старую отправку даже при выключенном V1-флаге. Нужен preflight действующей конфигурации перед заменой; OFF — не изоляция legacy SMTP. Ключ восстановления не менять, пока действуют связанные reset-запросы: это нарушит проверку производных токенов; ротация требует отдельного плана.

Существующий production ENV validator также требует `EMAIL_FROM` при настроенном SMTP. Сохранить/согласовать совместимый подтверждённый адрес для legacy-путей (отдельно от display-name формата `SMTP_FROM`), не удалять существующие EMAIL_* значения автоматически. Пустые или неподтверждённые legacy sender параметры — blocker preflight, а не причина отключать валидацию.

| Переменная | Контракт Release B |
| --- | --- |
| `NOTIFICATIONS_MAX_V1_ENABLED` | По умолчанию OFF; включение только точным `true`, независимо от email. До допуска `false`. |
| `MAX_BOT_TOKEN` | Действующий секрет официального бота. Передаётся API в заголовке `Authorization`, без query-параметров. |
| `MAX_BOT_URL` | Публичная ссылка именно этого бота: `https://max.ru/<имя_бота>`. Код допускает один сегмент из букв ASCII, цифр, `_`, `-`; без порта, query, hash и credentials. Это не API URL и не webhook URL. |
| `MAX_WEBHOOK_SECRET` | Независимый случайный секрет 32–256 символов; для совместимости использовать ASCII-буквы/цифры/`_`/`-`. То же значение задаётся полем `secret` подписки. |

В текущем adapter API origin фиксирован: `https://platform-api2.max.ru`. Переменных `MAX_API_URL` и `MAX_WEBHOOK_URL` реализация не читает. Адрес подписки задаёт владелец в MAX: `https://body-state.ru/api/integrations/max/webhook`. Существующие DB/Redis/cron credentials сохраняются; новые значения здесь не вводятся. Для cron сохранить действующую авторизацию и частоту, согласовать итоговое подключение V1-worker с Петровичем.

## Release A: действия владельца Postbox

### Sender и доступ

1. До изменений зафиксировать текущие sender identities и разрешённые отправляющие сервисы домена, проверить действующий SMTP/Reply-To и влияние общих env на legacy. Не заменять настройки вслепую.
2. В нужном каталоге YC открыть Cloud Postbox → создать адрес с доменом `body-state.ru` либо проверить существующий. Выбрать DKIM-режим. Проверить список разрешённых отправителей: он должен разрешать именно выбранный `no-reply@body-state.ru` (или другой согласованный sender); имя бренда не заменяет разрешение адреса.
3. Создать/выбрать сервисный аккаунт в том же каталоге, что и адрес Postbox; назначить роль `postbox.sender`. Создать API-ключ со scope `yc.postbox.send`. ID и секретную часть передать в защищённое runtime env как `SMTP_USER`/`SMTP_PASSWORD`. Для выбранной схемы API-key секрет используется непосредственно; инструкция преобразования static access key к ней не относится.
4. Проверить доступность порта 587 из целевого runtime и цепочку сертификатов с обязательным STARTTLS. Это отдельный согласованный preflight, не реальная отправка из unit-тестов.

Источники: [создание адреса](https://yandex.cloud/en/docs/postbox/operations/create-address), [отправка и SMTP/API-key](https://yandex.cloud/en/docs/postbox/operations/send-email).

### DKIM и подтверждение домена

1. Открыть выбранный адрес → настройки DKIM. При Easy DKIM скопировать обе выданные сервисом пары CNAME name/value в авторитетную DNS-зону. Не придумывать selector/target и не заменять существующий DKIM другого отправителя.
2. Оба CNAME оставить после подтверждения: они нужны автоматической ротации. У DNS-провайдера проверить, ожидает ли поле имени FQDN или имя относительно зоны; избежать удвоения `body-state.ru`.
3. Если существующая identity использует Advanced DKIM, опубликовать ровно выданный для неё TXT `<selector>._domainkey.body-state.ru` с публичным ключом. Приватный DKIM-ключ не публиковать и не переносить в репозиторий. Не смешивать TXT/CNAME на одном имени.
4. Дождаться обновления DNS и статуса успешной проверки в Postbox. Проверить ответы авторитетных и внешних резолверов; при задержке учитывать TTL, затем повторить проверку в консоли. Зафиксировать только безопасное evidence статуса, без ключей и адресов получателей.

Источник: [проверка домена и оба режима DKIM](https://yandex.cloud/en/docs/postbox/operations/check-domain).

### SPF и DMARC

1. Получить текущие TXT корня `body-state.ru` и `_dmarc.body-state.ru` до редактирования. Сохранить разрешения существующих отправителей.
2. В единственную SPF-запись добавить `include:spf.postbox.yandexcloud.net` перед завершающим `all`. Не создавать второй TXT с `v=spf1`. Если SPF отсутствует, исходный вариант YC: `v=spf1 include:spf.postbox.yandexcloud.net ~all`. Проверить суммарный лимит SPF DNS lookup и отсутствие `PermError`; не ослаблять существующую политику без согласования.
3. DMARC публикуется TXT на `_dmarc.body-state.ru`. Если записи нет, вариант для первоначального наблюдения — `v=DMARC1;p=none`; он не блокирует подмену. Адрес для `rua`, если нужен, владелец отдельно создаёт и согласует. Существующие `quarantine`/`reject` не понижать автоматически.
4. После разрешённого контрольного письма проверить исходные заголовки: SPF, DKIM и DMARC, включая alignment с доменом From. Разобрать расхождения до массового включения. Усиление DMARC согласовать после проверки всех легитимных отправителей.

Источники: [DNS/SPF](https://yandex.cloud/en/docs/postbox/concepts/dns-records), [DMARC](https://yandex.cloud/en/docs/postbox/operations/setup-dmarc). Эти шаги описывают требуемую настройку, а не подтверждают существующий DNS.

### Квоты и ответы

В Cloud Quota Manager владелец проверяет фактически выделенные `postbox.send.rate` и `postbox.emails_sent.count`, использование за 24 часа, запас под записи, reset и reminders. Документация на дату сверки указывает базовые значения 1 письмо/с и 200 писем/24 часа; это не доказательство квот данного облака. При нехватке запросить повышение через Quota Manager/поддержку до включения. Подать запрос может пользователь с `quota-manager.requestOperator` или более высокой ролью.

Сеня и Петрович должны подтвердить, что суммарная скорость всех worker/legacy-отправителей укладывается в реальную квоту: локальные timeout/backoff не являются глобальным rate limiter. Проверить suppression/bounce-состояние согласованных тестовых адресов и безопасный мониторинг отказов. `SMTP_REPLY_TO` должен вести в реально обслуживаемый ящик; отправить тестовый ответ можно только в согласованном smoke-тесте. Postbox SMTP не создаёт ящик поддержки.

Источник: [квоты и лимиты](https://yandex.cloud/en/docs/postbox/concepts/limits).

## Release B: действия владельца MAX

1. Владелец проходит верификацию профиля на [MAX для бизнеса](https://business.max.ru), создаёт официального бота и проходит требуемое одобрение/модерацию. До подтверждения этих условий использовать fake-provider; готовность к реальной доставке не заявлять. Получить токен в настройках бота, проверить соответствие публичной ссылки и токена одному боту. Токен и webhook secret — разные секреты.
2. Перед включением проверить исходящий HTTPS к `platform-api2.max.ru`. Официальная документация требует доверия сертификатам Минцифры: при необходимости Сеня устанавливает проверенную официальную цепочку в доверенное хранилище runtime по отдельному согласованию. Проверку сертификатов не отключать.
3. Проверить публичный endpoint HTTPS на 443, совпадение имени с SAN/CN, полную доверенную цепочку, отсутствие login/redirect, корректную прокси-передачу POST, тела и `X-Max-Bot-Api-Secret`. При OFF приложение возвращает 503: это ожидаемо, подписку на выключенный канал не регистрировать.
4. После допуска включить MAX в согласованном окружении и создать подписку через `POST /subscriptions`: `url` — указанный выше webhook, `update_types` — только `["message_created"]`, `secret` — runtime `MAX_WEBHOOK_SECRET`. Текущий parser не принимает `bot_started`; не копировать список событий из общего примера API. Проверить созданную подписку через `GET /subscriptions`. Long Polling одновременно не запускать.
5. Проверить 401 при неверном секрете, отказ от некорректных/слишком больших payload, дедупликацию повторов и 200 только после успешного durable принятия. MAX ожидает ответ за 30 секунд; регистрация и проверка подписки — отдельные разрешённые операции владельца, здесь не выполнялись.

Источники: [подключение профиля](https://dev.max.ru/docs/maxbusiness/connection), [создание бота](https://dev.max.ru/docs/chatbots/bots-create/create), [API и токен](https://dev.max.ru/docs-api), [webhook: HTTPS, secret, события](https://dev.max.ru/docs-api/methods/POST/subscriptions).

Пользователь сам начинает личный диалог с ботом и вводит код из авторизованного кабинета. Код текущей реализации действует пять минут. Проверить привязку, истечение/повторное использование, конфликт identity, unlink/relink и отсутствие отправки после unlink. Нельзя привязывать по совпадению имени/телефона. Административные отправки требуют отдельной проверки роли и identity; наличие общего adapter не доказывает готовность этого сценария. Отсутствие одобренного MAX не блокирует независимый допуск Release A.

## Protected, uncertain и ручной разбор

### Обязательная граница активации

Для каждого разрешённого включения задать `NOTIFICATIONS_EMAIL_V1_ACTIVE_SINCE` / `NOTIFICATIONS_MAX_V1_ACTIVE_SINCE` — точный новый UTC timestamp вида `2026-10-15T18:00:00Z` (пример, не готовое значение). Значение сохраняется монотонно в `notification_channel_activation`. При повторном включении после OFF нужен новый timestamp; уменьшение границы блокируется. Без корректной границы V1 не создаёт отправки. Это часть release preflight, а не право менять runtime env.

Worker отбрасывает события до границы, сервисные события старше 30 минут, reminders с опозданием более 5 минут; reset дополнительно ограничен TTL и одноразовым токеном. Нет автоматической догонки старых отправок. V1 теперь имеет отдельный POST `/api/cron/notifications-v1` и отдельный system-only minute guard; daily reminders сохраняет только legacy sync/queue и прежнее время. Runtime `NOTIFICATIONS_V1_SCHEDULER_ENABLED` по умолчанию false, DB022 worker control по умолчанию paused. См. [scheduler runbook](../POSTBOX-SCHEDULER-RELEASE-RUNBOOK.md): отдельная установка/активация требует GO, production cron этим PR не меняется. Нужны явные подтверждённые SMTP budget limits/scope/legacy reserve, описанные там; значения фактических tenant-квот по-прежнему предоставляет владелец. Квоты не выводятся из SMTP AUTH или общих значений документации.

### Откат после schema022

Миграция расширяет schema021, но старый V2 worker не знает `engine=v1`, новых account/MAX событий и nullable booking ID. Поэтому прежний image нельзя считать готовым notification fallback. Безопасная первичная мера — оставить текущую engine-aware сборку, выключить новые флаги согласованным способом и сохранить очередь. Если требуется откат к старому image, сначала отдельно согласовать и проверить fencing reminders source; не возобновлять старый worker над смешанной очередью. Таблицы и события не удалять, schema022 обратно не мигрировать. Платёжные и booking таблицы не меняются.

Запрещены массовый replay, cleanup и перевод исторических/protected уведомлений в V1. Не менять их engine, ключи, attempts или статусы для «догонки». Выключенный флаг не даёт права включать старую очередь заново.

`uncertain` означает, что провайдер мог принять сообщение, а локальное подтверждение потерялось (timeout, разрыв, падение worker). Автоматический и ручной replay таких строк запрещён. Сначала безопасная сверка provider message ID/времени/статуса у провайдера ответственным владельцем; отсутствие ID не доказывает неотправку. Не переводить `uncertain` в `retry`/`queued` прямым SQL.

Ручной retry допустим только через проверенный административный механизм для разрешённых состояний и актуального бизнес-события после устранения причины. Проверить revision/status записи, канал, действующую привязку, срок reset-token и отсутствие уже принятого логического уведомления. Если механизма или доказательств нет, оставить на ручном разборе. Исключительное решение о новой отправке требует отдельного конкретного разрешения владельца с учётом риска дубля; это не разрешение replay существующей строки.

В отчёте разбора оставлять категорию ошибки и безопасные технические идентификаторы; не публиковать email/телефон, текст сообщения, reset URL/token, SMTP/MAX credentials и webhook secret. Ошибка уведомления не меняет booking/payment lifecycle. Email об оплате не заменяет фискальный чек.

## MAX administrative-only rollout

For an explicitly approved admin-only launch set both
`NOTIFICATIONS_MAX_V1_ENABLED=true` and `NOTIFICATIONS_MAX_V1_ADMIN_ONLY=true`,
with a fresh `NOTIFICATIONS_MAX_V1_ACTIVE_SINCE`. The master flag alone preserves
the previous full-rollout behavior and is not an admin-only switch.

Admin-only mode disables customer pairing APIs, code consumption, customer MAX
enqueue, queue claiming/recovery, and transport even for existing bindings.
Existing customer rows/bindings are retained. Email policy is unchanged. Webhook
accepts only the authenticated `message_created` path; matching admin codes create
pending identity only. The owner must independently confirm the dialog in the
admin UI before administrative delivery is allowed. A previous bot "Start" is
not pairing or proof of webhook delivery. Invalid mode values fail closed.
