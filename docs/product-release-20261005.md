## Что изменилось

Клиент после записи получает сохранённую карточку: название услуги, московское
время, фактическую длительность слота, адрес из настроек, фиксированную стоимость
и скидку, способ и состояние оплаты, следующий шаг, защищённое управление и ICS.
Неуказанные адрес, подготовка и историческая цена показываются честно, без выдуманных
данных. В существующих настройках не найдено отдельного поля подготовки.
Оплата на приёме означает подтверждённую запись, но не полученную оплату.
Неявка и завершённая запись без явной посещаемости не называются состоявшимся приёмом.

Объединены существующие формы трёх направлений и формы психологических программ
с бронированием слота. Сохранены выбор очно/онлайн, ограничения оплаты, профиль,
нормализация телефона, промокоды и отдельное согласие. Повтор сетевого запроса
с тем же ключом и секретом возвращает прежнюю запись. Кнопки формы блокируются
сразу, включая двойной клик. Гость получает секретную ссылку с ключом во фрагменте;
сервер хранит только SHA-256. В кабинете добавлен переход к деталям своих записей.
Ссылку нельзя публиковать: обладатель ключа может управлять соответствующей записью.

При известном отказе Init бронь остаётся до сохранённого срока; повторная оплата
не создаёт новую запись. Существующий незавершённый платёж с URL используется
повторно. Таймаут, неоднозначный ответ шлюза или ошибка сохранения принятого банком
Init открывают разбор и блокируют новый Init. Успех определяет callback/существующая
серверная сверка, не переход на success. Просроченную бронь очищает существующий
cron; до его запуска время может оставаться занятым, но начать новый платёж после
сохранённого срока уже нельзя. Проверки действительности, принадлежности и лимитов
промокода при оплате сохранены: если условия административно изменены, возвращается
ошибка, а не молча пересчитывается сохранённая цена.

Уведомления теперь ставятся в постоянную очередь в одной транзакции с событием
записи. Журнал содержит связь, тип, канал, план, состояние, попытки, следующий запуск,
безопасную ошибку и ID провайдера. SMS и email независимы. Ключ уникальности включает
запись, направление, событие, ревизию и канал. Отмена, перенос и закрытие инвалидируют
устаревшие сообщения. Отправка проверяет актуальность повторно.

Параллельные обработчики используют `FOR UPDATE SKIP LOCKED`; проверка записи
и отправка сериализованы с изменениями расписания. Временная ошибка имеет максимум
четыре автоматические попытки с задержками 60/120/240 секунд. Счётчик попыток
сохраняется при ручной постановке. Принятое или неоднозначное сообщение не отправляется
повторно автоматически. Прерванная обработка через пять минут становится `uncertain`.
Это предотвращает слепые дубли, но не обещает распределённый exactly-once без поддержки
идемпотентности внешнего провайдера. Сетевой вызов удерживает блокировку расписания
до своего таймаута: это осознанный приоритет отсутствия устаревших отправок;
высокую нагрузку нужно оценить отдельной приёмкой.

В существующую административную сводку добавлен «Рабочий день»: выбранная московская
дата, приёмы, обращения, ожидающие действия, ожидаемая оплата на приёме, проблемы
уведомлений, открытые платежные случаи и агрегированные факты воронки. Ошибка
загрузки не превращается в сообщение «проблем нет». Прямые ссылки открывают
существующую карточку клиента. Журнал позволяет безопасно повторно поставить
неуспешное актуальное сообщение, но не принятое или неоднозначное.

Платёжный случай имеет открытое/разобранное состояние, результат, комментарий,
дату, автора и историю. В архитектуре один общий администратор, поэтому автор
фиксируется как `shared_admin`; новый каталог сотрудников не создавался. Разбор
не меняет статус банка и не возвращает отменённую запись в расписание. Отметка
«возврат оформлен отдельно» — заявление администратора о внешнем действии,
не выполнение и не автоматическая банковская проверка возврата.

Описание аналитики: [booking-funnel.md](booking-funnel.md).

## Общая инструкция миграции и отката

1. Получить отдельное разрешение на выпуск и сделать резервную копию БД.
2. На целевом окружении приостановить cron и запись новых операций на короткое
   окно применения; выполнить существующий `scripts/migrate.mjs`, включая 019,
   до запуска новой версии приложения. Прогнать приёмку сначала на тестовом окружении.
3. Запустить новую версию, проверить health, права, запись и журналы; затем
   включить существующий `reminders` регулярно, например каждую минуту,
   а `cancel-pending` по прежнему частому расписанию. Один вызов обрабатывает
   до 20 сообщений, поэтому частота должна соответствовать нагрузке.
   Новый отдельный cron endpoint не требуется. Несколько запусков безопасны.
4. 019 аддитивна: старые записи имеют NULL для снимка/секрета/срока. Старые цены
   не восстанавливаются по текущему прайсу; детали доступны владельцу аккаунта,
   но нет искусственно созданного гостевого ключа и нельзя скачать ICS без снимка.
   Cron использует прежние 10 минут как fallback для исторической брони.
   Уже отмеченные старым кодом отправленные напоминания не дублируются.
5. Откат приложения не равен откату данных. Сначала остановить новый обработчик
   и изменяющие операции, сохранить БД и проверить совместимость предыдущей версии.
   Не удалять таблицы очереди/истории и новые поля после появления записей.
   Предыдущая синхронная отправка не учитывает новый журнал и может вызвать повтор:
   при откате нельзя просто включать старую отправку без сверки. Down-миграции нет.

В этом каталоге Git не настроен. До изменений сохранена локальная копия исходников
`artifacts/product-release-before-20261005.tar.gz` без env-файлов. Это не резервная
копия БД и не готовая команда отката production.

## Проверки и границы доказательств

Пройдено 34 интеграционных сценария на отдельном PostgreSQL 17 в Docker.
`npx tsc --noEmit`, `npx eslint .` и оптимизированная сборка Next.js также пройдены.
Без локальной сессии новые административные API проверены HTTP-запросами: 401.
Проверены конкурентные 90-минутные записи, откат неудачного INSERT,
идемпотентность оплаты и посещения, владение аккаунтом, гонки переноса/очистки,
подпись callback и сумма, отсутствие автоматического начисления по времени,
повтор запроса записи, гостевой доступ, неизменность цены, ICS и Unicode folding,
параллельные воркеры, независимые каналы, временный сбой/лимит повторов,
неоднозначная отправка, безопасный ручной повтор, устаревшие напоминания,
сохранение брони при отказе Init и push, шлюз 502, поздняя оплата отмены,
история разбора без изменения банковского факта, авторизация новых API,
обезличивание аналитики и повторное применение миграции к исторической записи.

Провайдеры SMS/email и Т-Банк в автоматических тестах заменены заглушками.
Браузер использовал реальные локальные API/БД/Redis, но пустые ключи внешних сервисов.
Проверены создание записи с оплатой на приёме, мобильная защищённая карточка,
реальный тестовый вход администратора, смена дня, журнал, постановка повторной
отправки, переход в карточку и сохранение комментария платёжного разбора.
Проверки компоновки выполнены при запросе 390×844 (внутренняя ширина 375)
и 1440×1000: горизонтального переполнения новых экранов не обнаружено.
Снимки сохранены в `artifacts/*-mobile.png` и `artifacts/*-desktop.png`.

Нужна отдельная внешняя приёмка: реальные credentials/песочница банка,
callback и возврат через банк, SMS, внешний Umami. Почта остаётся отключённой
до выбора сервиса. Транспорт сейчас фиксирует принятие, а не доставку:
`delivered` поддержан и проверен положительным тестовым результатом, но настоящий
webhook/polling подтверждения доставки выбранного провайдера не подключён.
До этого реальные сообщения остаются `accepted`, без ложного «доставлено».
Продукт нельзя объявлять проверенным на реальном эквайринге или доставке по этим тестам.

## Как проверить локально

Только синтетическое окружение; не используйте `.env.local` как тестовую БД.
Изолированные контейнеры этого релиза уже запущены:
`doctor-journey-postgres` на 127.0.0.1:15432 и `doctor-journey-redis` на
127.0.0.1:16379. Остальные контейнеры пользователя не изменялись.

Если эти два контейнера отсутствуют, создайте только их:

```powershell
docker run --rm -d --name doctor-journey-postgres -p 127.0.0.1:15432:5432 -e POSTGRES_USER=doctor_qa -e POSTGRES_PASSWORD=doctor_qa_local_only -e POSTGRES_DB=audit_regression_2026100501 postgres:17-alpine
docker run --rm -d --name doctor-journey-redis -p 127.0.0.1:16379:6379 redis:8-alpine
node scripts/prepare-journey-qa.cjs
node scripts/run-journey-qa.cjs dev -p 3100
```

Откройте http://localhost:3100/rehabilitation и http://localhost:3100/login.
Тестовый логин `qa-admin`, пароль — в `.env.journey-qa.example`. Скрипт prepare
создаёт только локальный тестовый пароль и окна на три следующих дня.
Сервисы имеют глобальное расписание: бронь одной процедуры может занять
пересекающееся окно другого направления — это сохранённая гарантия.

Для полного интеграционного прогона выберите НОВОЕ имя БД указанного формата:

```powershell
$env:AUDIT_DATABASE_NAME='audit_regression_' + (Get-Date -Format yyyyMMddHHmmss)
docker exec doctor-journey-postgres createdb -U doctor_qa $env:AUDIT_DATABASE_NAME
node scripts/build-audit-tests.cjs
node --env-file=.env.journey-qa.example artifacts/audit-runtime/tests/audit-regressions.cjs
npx tsc --noEmit
npx eslint .
node scripts/run-journey-qa.cjs build
```

Набор не очищает БД и предназначен для нового синтетического экземпляра.
Для локального запуска очереди после создания тестовой записи:

```powershell
Invoke-RestMethod -Uri http://localhost:3100/api/cron/reminders -Headers @{Authorization='Bearer local-journey-cron-only'}
```

Без конфигурации отправщиков результатом будет «канал не настроен», а не отправка.
QA-контейнеры созданы с `--rm`, без постоянного volume: при их остановке
синтетическая БД удаляется. Не останавливайте чужие контейнеры и не используйте
`docker compose down` для других проектов.
